# مرجع قاعدة بيانات صيدليات وعيادات العوضي

هذا المجلد هو نقطة البداية لأي مطور أو نموذج ذكاء اصطناعي جديد. المشروع يستخدم Supabase واحدًا لخدمة موقع العملاء ولوحة الصيدلية ولوحة العيادات. اقرأ هذا الملف ثم `PROJECT_STATUS.md` قبل تعديل SQL أو الواجهة.

## شكل المجلد

```text
Schema SQL/
├── README.md                         دليل التشغيل والسياق
├── 01_pharmacy_schema.sql            تأسيس جداول الصيدلية الأساسية
├── 02_clinics_schema.sql             تأسيس جداول العيادات وربطها
├── 03_migrations.sql                 ترقيات وإصلاحات الأمان بالتسلسل
├── 04_verify_all.sql                 فحوص SQL مفصلة، قراءة فقط
├── 05_audit_json.sql                 تدقيق مجمّع JSON، قراءة فقط
├── 06_frontend_auth_changes.md       توثيق تعديل تسجيل الدخول
└── PROJECT_STATUS.md                 حالة المشروع والقرارات المفتوحة
```

## تشغيل قاعدة جديدة

1. شغّل `01_pharmacy_schema.sql` في Supabase SQL Editor.
2. شغّل `02_clinics_schema.sql` بعده. الملف يجمع أربع خطوات تأسيسية بالترتيب الموضح في رأسه.
3. شغّل `03_migrations.sql` كاملًا. فيه ترقيات مرقمة ومجمعة مع الحفاظ على ترتيبها المنطقي.
4. شغّل `04_verify_all.sql` قسمًا قسمًا، ثم راجع النتيجة. `05_audit_json.sql` بديل مختصر يرجع صف JSON واحد.
5. راجع تعديلات الواجهة المنشورة كما في `06_frontend_auth_changes.md` و`PROJECT_STATUS.md`.

## تشغيل قاعدة موجودة

لا تعِد تشغيل ملفات التأسيس على قاعدة قائمة لمجرد التحقق. استخدم `04_verify_all.sql` أو `05_audit_json.sql` أولًا، ثم طبّق فقط migrations الناقصة بعد مطابقة الحالة الفعلية. ملفات migrations الفردية الأصلية باقية في مجلد لوحة الصيدلية كسجل تغيير قابل للمراجعة.

## تنبيهات مهمة

- `01_pharmacy_schema.sql` و`02_clinics_schema.sql` هما ملفا تأسيس منفصلان؛ لا تدمجهما في ملف SQL واحد لأن بعض جداول العيادات تعتمد على جداول الصيدلية، كما أن سجل العيادات الأصلي نفسه incremental.
- `02_clinics_schema.sql` يحتوي سياسات قديمة واسعة ضمن تاريخ التأسيس؛ إكمال migrations الأمنية ضروري قبل استخدام النظام.
- `03_migrations.sql` هو الملف الموحّد لتغييرات SQL الأمنية، ويحتفظ بترويسات المصدر. الملفان الأصليان `14_final_create_order.sql` و`14_create_order_rpc_fix_medications_field.sql` متطابقان حرفيًا؛ أُدرج محتواهما مرة واحدة فقط تحت اسم المصدر الأول.
- migration `16_lock_direct_order_insert.sql` يحذف إدخال الطلبات العام؛ المسار المتوقع للعميل هو `create_order()` فقط.
- migration `17_consultations_branch_lock.sql` يعالج سياسة قراءة صيدلي واسعة قد تكون أُنشئت يدويًا، ويجعل الاستشارات غير المستلمة مرئية للفروع، ثم يحصر الاستشارة المستلمة بفرعها.
- `04_verify_all.sql` للقراءة فقط. اختبارات `create_order` الحية داخله معطلة بالتعليق لأنها تنشئ طلبًا فعليًا عند تفعيلها.
- ملف `Schema SQL.txt` في جذر المشروع كان وصفًا قديمًا ومقتضبًا، وليس سجل migrations كاملًا؛ استخدم هذا الدليل والمجلد بدلًا منه.
- ملفات `00_audit_current_policies.sql` و`00_verify_setup.sql` داخل مجلد الصيدلية وُحّدت أرقام نسخها هنا كـ `04` و`05` لتوضيح الفرق: تفصيلي متعدد النتائج مقابل ملخص JSON.

## مصدر كل ملف موحّد

- `01_pharmacy_schema.sql`: `Admin File - Pharmacy Dashboard/Schema SQL/schema.sql`.
- `02_clinics_schema.sql`: ملفات SQL الأربعة داخل `Admin File - Elawadi Clinics Dashboard/SQL/`.
- `03_migrations.sql`: ملفات SQL ذات الأرقام `01` إلى `08` و`10` إلى `17` من مجلد SQL الصيدلية. تعديل الواجهة `09_auth_js_diff.md` محفوظ منفصلًا في `06_frontend_auth_changes.md`، وليس SQL.
- `04_verify_all.sql` و`05_audit_json.sql`: نسختا التحقق السابقتان بعد تحديث وصف الحالة النهائية.

## احتياطات أمنية لا تُنسى

- لا تضع `service_role` أو مفاتيح سرية في JavaScript بالمتصفح.
- لا تمنح دور admin عند غياب صف profile؛ يجب أن يوجد profile نشط ومصرّح به في قاعدة البيانات.
- سياسات RLS permissive تتحد بـ OR. راجع كل السياسات الموجودة فعليًا قبل إضافة policy جديدة، واحذف أي سياسة قديمة واسعة يدويًا أو ضمن migration.
- عند كتابة policy تفحص صلاحية من نفس الجدول، استخدم helper آمنة مثل `is_clinic_admin()` لتجنب infinite recursion.
- إعدادات Supabase Auth من لوحة التحكم ليست جزءًا من SQL ولا يستطيع ملف التحقق تأكيدها.
